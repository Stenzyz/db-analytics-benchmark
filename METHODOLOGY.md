# Методика измерений

Этот документ описывает, как проводятся замеры, какие приняты правила и какие у
результатов ограничения. Методика важнее конкретных цифр: именно она отличает
инженерный бенчмарк от разового запуска запроса.

## 1. Принципы

1. **Фиксация окружения.** До начала замеров записываются процессор, объём
   оперативной памяти, тип накопителя, операционная система, версии всех трёх
   СУБД и параметры контейнеров. См. `results/environment.txt` (заполняется
   командой `make env`). Без этих данных цифры несопоставимы.

2. **Повторность.** Каждый запрос выполняется не менее пяти раз. В итоговую
   таблицу идёт медиана; дополнительно приводятся минимум и максимум. Медиана
   устойчивее среднего к единичным выбросам.

3. **Прогрев.** Первый прогон каждого запроса отбрасывается как прогрев и в
   расчёт не входит. Это зафиксировано в коде `run_benchmark.py`.

4. **Холодный и горячий кэш.** Замеры разделяются на два режима:
   - Горячий: запрос уже прогрет, данные в кэшах. Режим `--mode hot`.
   - Холодный: перед каждым запросом сбрасываются кэши. Режим `--mode cold`.
     Для ClickHouse выполняются `SYSTEM DROP MARK CACHE` и
     `SYSTEM DROP UNCOMPRESSED CACHE`. Кэш страниц операционной системы из
     контейнера надёжно не сбрасывается, поэтому холодный режим считается
     «холодным на уровне СУБД, но не на уровне ОС», и это прямо оговаривается
     в выводах. Для PostgreSQL и MySQL полноценный холодный замер требует
     перезапуска сервиса или сброса страничного кэша ОС; если это не
     выполнялось, замеры по ним приводятся только как горячие.

5. **Одна переменная за раз.** В каждом эксперименте между сравниваемыми
   конфигурациями отличается ровно один параметр: ключ сортировки, либо
   партиционирование, либо наличие предрасчёта, либо СУБД. Данные и запрос при
   этом идентичны.

6. **Запросы приводятся полностью.** Все тестовые запросы лежат в `sql/` в том
   виде, в каком выполняются. В отчёте они не пересказываются.

7. **Сырые результаты сохраняются.** Выгрузки времени выполнения и полей из
   `system.query_log` ClickHouse сохраняются в `results/raw/`. Каждая цифра в
   README прослеживается до сырого файла.

## 2. Какие метрики снимаются

Для всех СУБД — время выполнения (медиана, минимум, максимум по пяти прогонам
без учёта прогрева).

Дополнительно, где это доступно:
- **ClickHouse** — прочитанные строки и байты из `system.query_log` (поля
  `read_rows`, `read_bytes`, `query_duration_ms`). Запрос помечается собственным
  `query_id`, по которому затем извлекается запись журнала. Это важнее времени:
  фраза «запрос прочитал 2 млн строк вместо 300 млн» показывает механизм, а не
  только наблюдаемый результат.
- **PostgreSQL** — план выполнения `EXPLAIN (ANALYZE, BUFFERS)`: фактические
  строки, обращения к буферам, использование индекса.
- **MySQL** — план выполнения `EXPLAIN` (при наличии — `EXPLAIN ANALYZE`).

## 3. Корректность сравнения трёх СУБД (Э5)

Сравнение СУБД между собой имеет смысл только при тождестве данных и запроса.
Поэтому:
- В PostgreSQL и MySQL переносится одно и то же подмножество строк, полученное
  одним детерминированным срезом из ClickHouse (`scripts/load_subset.py`).
- Число строк в трёх СУБД сверяется и фиксируется в отчёте.
- Логика запроса дословно одинакова; отличия диалектов (например, функции работы
  с датой) сведены к минимуму и оговорены.

Любое отклонение (иной объём, иной запрос) делает сравнение недействительным и
должно быть явно отмечено.

## 4. Ограничения

- Замеры выполнены на одной пользовательской машине в контейнерах Docker. Это не
  промышленный бенчмарк и не претендует на универсальность.
- СУБД работают с настройками по умолчанию; тонкая настройка не проводилась.
  Любые отклонения от дефолта (например, параметры в `docker-compose.yml`)
  перечислены в README.
- Сценарий аналитический (агрегация по диапазонам и группировкам). Выводы не
  переносятся на транзакционную нагрузку.
- Холодный кэш сбрасывается на уровне СУБД (для ClickHouse); кэш страниц ОС из
  контейнера не сбрасывается. Абсолютные значения холодных замеров следует
  читать с этой поправкой.
- Результаты отражают поведение на конкретном датасете (NYC Taxi) и конкретном
  наборе запросов. На других данных и запросах соотношение может измениться.

## 5. Как воспроизвести

Полная последовательность — в README, раздел «Как воспроизвести». Кратко:
`make up` → `make env` → `make load-ch` → `make load-subset` → `make bench`
(и при желании `make bench-cold`) → `make tables`.
